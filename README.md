# САМ ВКО — система автономного мониторинга качества интернет-соединения

Мониторинг каналов связи организаций образования Восточно-Казахстанской области:
**карта области → карточка школы → отдельный ПК-уровень прослеживания**.

174 организации · 618 ПК-агентов · 415 000+ замеров в демо-базе.

---

## 1. Архитектура

```
agent/                  ПК-агент (Python): замеры, локальный спул, Smart Sync
backend/
  app/
    config.py           настройки через переменные окружения
    database.py         PostgreSQL (прод) / SQLite (offline-демо)
    cache.py            Redis + прозрачный in-memory fallback
    security.py         JWT, mTLS, RBAC, неизменяемый аудит
    models.py           School · Device · Measurement · Incident · User · AuditLog · SyncBatch
    schemas.py          Pydantic-контракты
    routers/
      auth.py           Auth API    — вход, роли, журнал аудита, политики
      agent.py          Agent API   — регистрация ПК, приём замеров, Smart Sync
      web.py            Web API     — дашборд, карта, карточка школы, ПК-уровень
      admin.py          Admin API   — агенты, пользователи, коды развёртывания
      ai.py             AI API      — досудебные претензии, PDF-акты SLA
    services/
      status.py         единые правила классификации качества и SLA
      smart_sync.py     очередь и воркеры офлайн-догрузок
      celery_app.py     Celery/RabbitMQ-вариант той же очереди
      predictive.py     поиск паттернов деградации, оценка риска
      reports.py        генерация PDF-акта (ReportLab)
      ml/               «Виновник» — машинное обучение
        linmodel.py     softmax-регрессия на чистом Python (веса в JSON)
        baseline.py     сезонный базис «час × тип дня», детектор аномалий
        features.py     признаки радиуса поражения и предвестники пробоя SLA
        attribution.py  вердикт «кто виноват» + доказательная база
        forecast.py     вероятность выхода за SLA на 6 часов вперёд
        train.py        обучение на журнале аварий и истории замеров
  bootstrap.py          миграция схемы, учётные записи, симулятор отказов, обучение
  models/               артефакты моделей: веса, профили базиса, отчёт обучения
frontend/               React 19 + Vite + Mapbox GL + Recharts
```

**Фреймворк.** FastAPI — асинхронная обработка конкурентных запросов агентов;
OpenAPI-схема доступна на `/docs` (41 эндпоинт).

**База данных.** PostgreSQL для реляционных сущностей и time-series замеров.
Индексы `(school_id, timestamp)` и `(device_id, timestamp)` под выборки графиков.
Для локального прогона без инфраструктуры автоматически используется SQLite.

**Кэш.** Redis держит агрегаты дашборда (TTL 10 с) и счётчики rate-limiting.
При недоступности Redis модуль `cache.py` переходит на процессный кэш —
демо не падает, а поведение API не меняется.

## 2. Безопасность

| Мера | Реализация |
|---|---|
| Защищённый канал | HTTPS/TLS обязателен (`VKO_VERIFY_TLS`), поддержан VPN-контур; HSTS вне режима отладки |
| Аутентификация устройства | JWT с привязкой к SHA-256 **отпечатку оборудования** (`security.py:current_device`) |
| Защита от подмены Device/School ID | `school_id` берётся из БД, а не из тела запроса; несовпадение отпечатка → 403 |
| mTLS | отпечаток клиентского сертификата принимается от TLS-терминатора и сверяется с записью устройства (`REQUIRE_MTLS=true`) |
| Регистрация агента | одноразовый код развёртывания школы; неверный код отклоняется и пишется в аудит |
| RBAC | роли `admin · operator · school · provider`; школа видит только себя, поставщик — только свои линии |
| Rate limiting | 120 запросов/мин на агента, 600 на пользователя (Redis-счётчики) |
| Неизменяемый аудит | append-only журнал со сцепленными SHA-256 хэшами; `/api/auth/audit` проверяет целостность цепочки |
| Минимизация данных | собираются только сетевые метрики и служебные контакты; персональные данные учащихся не хранятся |

## 3. Ключевые возможности

### Smart Sync — защита от Thundering Herd
Когда сотни офлайн-агентов одновременно возвращаются в сеть, `POST /api/agent/measurements/batch`
**не пишет в БД**: пакет регистрируется и ставится в очередь, клиент получает `202 Accepted`.
Запись выполняют фоновые воркеры с ограниченным параллелизмом и bulk-insert.
При переполнении очереди сервер отвечает `503` с `Retry-After` — агент повторит выгрузку
позже, данные не теряются. При заданном `CELERY_BROKER_URL` очередь уходит в RabbitMQ/Celery
с `rate_limit`, размазывающим пик во времени. Агент дополнительно стартует выгрузку
со случайной задержкой.

### Аналитика SLA и доказательная база претензии
`services/predictive.py` — статистический анализ накопленных замеров (без обучаемых
моделей): агрегация по дням недели и часам суток, сравнение с базовой линией и порогами
SLA. Находит воспроизводимые паттерны деградации («каждый понедельник просадка на 38%»),
считает соответствие SLA, стабильность канала и оценку риска 0–100 с прогнозом.
На этой базе `GET /api/ai/sla-report/{school_id}` формирует **PDF-акт фиксации нарушения SLA** —
приложение к досудебной претензии, а `POST /api/ai/claim/{incident_id}` генерирует саму
претензию (Gemini, с детерминированным юридическим шаблоном как fallback).

### «Виновник» — ML-атрибуция причины деградации

Главный контраргумент провайдера на любую претензию — «проблема у вас внутри».
Возразить одной точкой измерения нечем. Но агентов 618, и граница просадки видна:

| Что показывают замеры | Вердикт | Кто отвечает |
|---|---|---|
| 1 ПК из N, соседние ПК в норме | отдельный ПК или его линк | сисадмин школы |
| все ПК школы, соседние школы в норме | шлюз или ЛВС школы | обслуживающая организация |
| все школы провайдера в районе | узел провайдера | провайдер |
| все провайдеры района | магистраль / энергоснабжение | магистральный оператор |

**Слой 1 — сезонный базис.** Порог SLA (60% договора) не видит деградацию внутри
нормы: канал 100 Мбит/с, просевший с 95 до 62, формально «Норма». Поэтому качество
сравнивается не с договором, а с собственной нормой ПК в этот час и тип дня —
робастно, по медиане и MAD (48 корзин на агент).

**Слой 2 — классификатор радиуса поражения.** 13 признаков: доля поражённых ПК школы,
состояние шлюза, согласованность просадки, доли поражённых школ того же провайдера
в районе / других провайдеров в районе / того же провайдера в других районах, тип
линка и уровень Wi-Fi-сигнала. Вердикт сопровождается вкладом каждого признака —
объяснимо для оператора и для суда.

**Слой 3 — прогноз.** Вероятность выхода за SLA в ближайшие 6 часов по состоянию
канала за 1/6/24 ч и контексту района. Метки берутся прямо из истории замеров.

Результат подставляется в `POST /api/ai/claim/{id}` и в PDF-акт отдельным разделом
«Заключение об источнике нарушения». Обратный эффект не менее важен: если виновата
сама школа, система предупреждает, что претензия провайдеру доказательной
перспективы не имеет — сэкономленный выезд и несозданный репутационный риск.

**Как это обучено.** Модель — мультиномиальная логистическая регрессия на чистом
Python (`services/ml/linmodel.py`): десяток признаков, обучение за секунды, веса
лежат читаемым JSON. Внешних ML-зависимостей нет намеренно — система ставится на
школьные серверы и должна работать офлайн, где колёса под текущий Python могут быть
недоступны.

Разметка берётся из таблицы `fault_events`. Для холодного старта её наполняет
симулятор отказов в `bootstrap.py`: аварии рождаются на четырёх уровнях иерархии и
спускаются на замеры, порождая ту самую синхронность. В эксплуатации туда же ложатся
подтверждённые вердикты операторов (`POST /api/ml/verdict/{id}`) — цикл замыкается,
и переобучение опирается уже на реальные инциденты.

**Честно о метриках.** На отложенной выборке демо-данных атрибуция даёт
accuracy 0.976 и macro-F1 0.978, прогноз — 0.878 и 0.876. Высокие числа атрибуции
объясняются тем, что симулятор рисует чистые границы поражения; это корректная
оценка обучаемости на синтетике, но **не** продуктовая метрика. Настоящая проверка —
доля совпадений с вердиктами операторов после месяца эксплуатации, и она видна в
`/api/ml/model-info` по мере накопления меток. Прогнозные вероятности подрезаны
диапазоном 1–99%: взвешивание классов при обучении смещает калибровку, и модель не
вправе заявлять полную определённость.

### Динамическая конфигурация агента
Сервер сам управляет расписанием тестирования: «Норма» — 15 мин, «Нестабильно» — 3 мин,
«Критично» — 1 мин с переходом в углублённую диагностику. Новая конфигурация возвращается
в ответе на каждый замер (`config_version`), оператор может переключить режим вручную из
карточки ПК.

## 4. Запуск

```bash
# Backend
cd backend
pip install -r requirements.txt
python bootstrap.py              # миграция схемы + демо-данные (идемпотентно)
python main.py                   # http://localhost:8000/docs

# Frontend
cd frontend
npm install
npm run dev                      # http://localhost:5173

# ПК-агент
cd agent
pip install -r requirements.txt
export VKO_SCHOOL_CODE=VKO-RID-001
export VKO_ENROLL_SECRET=<код из раздела «Управление»>
python agent.py
```

Продакшн-конфигурация задаётся переменными окружения:

```bash
DATABASE_URL=postgresql+psycopg://user:pass@db:5432/vko
REDIS_URL=redis://cache:6379/0
CELERY_BROKER_URL=amqp://guest:guest@rabbitmq:5672//
JWT_SECRET=<секрет>
REQUIRE_MTLS=true
GENAI_TOKEN=<ключ Gemini>
DEBUG=false
```

### Демо-доступы

| Логин | Пароль | Что видит |
|---|---|---|
| `admin@vko.edu.kz` | `admin123` | всю область, аудит, управление агентами |
| `operator@vko.edu.kz` | `operator123` | мониторинг и работу с инцидентами |
| `school@vko.edu.kz` | `school123` | только свою организацию |
| `provider@kaztelecom.kz` | `provider123` | только линии своего провайдера |

## 5. Интерфейс

Светлая панель на **Manrope** (интерфейс) и **JetBrains Mono** (числовые метрики).
Знак приложения и подвал бокового меню используют логотипы проекта: Акимат ВКО,
Oskemen Hub и «Цифровой ВКО» (`frontend/public/logos/`).

- **Карта области** — тепловая карта качества связи, точки школ и спутниковая подложка;
  всплывающая карточка на маркере, KPI-полоса, правая колонка со сводкой, рейтингом риска
  нарушения SLA, инцидентами и проблемными ПК.
- **Карточка школы** — метрики канала, графики скорости/задержки, анализ соответствия SLA
  с паттернами деградации, список ПК-агентов, контакты, инциденты, выгрузка акта PDF.
- **Диагностика** — доска вердиктов «кто виноват» с доказательной базой по каждой
  организации, распределение ответственности по области (провайдер против школы),
  очередь прогноза пробоя SLA и карточка моделей с метриками и переобучением.
- **ПК-уровень** — по каждому компьютеру: собственная история канала, доступность агента,
  соответствие SLA, инвентарь и отпечаток оборудования, динамическая конфигурация,
  журнал офлайн-догрузок Smart Sync.

Палитра графиков (`#2F6BF6 · #0E9C8A · #D9730D · #B23A8E`) проверена на различимость
при нарушениях цветовосприятия; двойных осей нет — скорость и задержка разведены
по отдельным полотнам.
