# САМ ВКО — система автономного мониторинга качества интернет-соединения

Мониторинг каналов связи организаций образования Восточно-Казахстанской области:
**карта области → карточка школы → отдельный ПК-уровень прослеживания**.

181 организация ВКО · реальные GPS-координаты из OpenStreetMap · 618 ПК-агентов · 415 000+ замеров в демо-базе.

---

## 1. Архитектура

```
agent/                  ПК-агент (Python): замеры, локальный спул, Smart Sync
backend/
  app/
    config.py           настройки через переменные окружения
    database.py         PostgreSQL (прод) / SQLite (offline-демо)
    cache.py            Redis + прозрачный in-memory fallback
    security.py         JWT, mTLS, RBAC, неизменяемый аудит
    models.py           School · Line · Device · Measurement · Threshold · Incident · User · AuditLog · SyncBatch
    schemas.py          Pydantic-контракты
    routers/
      auth.py           Auth API    — вход, роли, журнал аудита, политики
      agent.py          Agent API   — регистрация ПК, приём замеров, Smart Sync
      web.py            Web API     — дашборд, карта, карточка школы, ПК-уровень
      admin.py          Admin API   — агенты, линии, пороги, пользователи, коды развёртывания
      export.py         выгрузка измерений CSV/XLSX (ТЗ п.9)
      ai.py             AI API      — досудебные претензии, PDF-акты SLA
    services/
      status.py         пороги (ТЗ п.11), классификация замеров, свежесть данных
      lines.py          основная/резервная линии, стартовые пороги
      smart_sync.py     приём замеров, надёжная очередь офлайн-догрузок, инциденты
      celery_app.py     Celery/RabbitMQ-вариант той же очереди
      predictive.py     поиск паттернов деградации, оценка риска
      reports.py        генерация PDF-акта (ReportLab)
      ml/               «Виновник» — машинное обучение
        linmodel.py     softmax-регрессия на чистом Python (веса в JSON)
        baseline.py     сезонный базис «час × тип дня», детектор аномалий
        features.py     признаки радиуса поражения и предвестники пробоя SLA
        attribution.py  вердикт «кто виноват» + доказательная база
        forecast.py     вероятность выхода за SLA на 6 часов вперёд
        train.py        обучение на журнале аварий и истории замеров
  bootstrap.py          миграция схемы, учётные записи, симулятор отказов, обучение
  import_vko_osm.py     импорт реальных координат школ ВКО из OpenStreetMap
  models/               артефакты моделей: веса, профили базиса, отчёт обучения
frontend/               React 19 + Vite + Mapbox GL + Recharts
```

**Фреймворк.** FastAPI — асинхронная обработка конкурентных запросов агентов;
OpenAPI-схема доступна на `/docs` (41 эндпоинт).

**База данных.** PostgreSQL для реляционных сущностей и time-series замеров.
Индексы `(school_id, timestamp)` и `(device_id, timestamp)` под выборки графиков.
Для локального прогона без инфраструктуры автоматически используется SQLite.

**Кэш.** Redis держит агрегаты дашборда (TTL 10 с) и счётчики rate-limiting.
При недоступности Redis модуль `cache.py` переходит на процессный кэш —
демо не падает, а поведение API не меняется.

## 2. Безопасность

| Мера | Реализация |
|---|---|
| Защищённый канал | HTTPS/TLS обязателен (`VKO_VERIFY_TLS`), поддержан VPN-контур; HSTS вне режима отладки |
| Аутентификация устройства | JWT устройства; отпечаток оборудования в токене сверяется с записью в БД (`security.py:current_device`). Это отсекает токены, выданные до перерегистрации, но **не доказывает**, что запрос пришёл с исходного ПК: токен вместе с файлом состояния агента можно скопировать. Привязку к железу даёт только mTLS (`REQUIRE_MTLS`); без него компенсирующие меры — отзыв устройства и аудит |
| Защита от подмены Device/School ID | `school_id` берётся из БД, а не из тела запроса; перерегистрация отозванного устройства запрещена, перенос Device ID на другое оборудование возможен только после сброса администратором |
| mTLS | отпечаток клиентского сертификата принимается от TLS-терминатора (заголовок обязан вычищаться на входе) и сверяется с записью устройства (`REQUIRE_MTLS=true`); при регистрации берётся из заголовка, а не из тела запроса |
| Регистрация агента | код развёртывания школы — **постоянный, не одноразовый**; неверный код отклоняется и пишется в аудит |
| RBAC | роли `admin · operator · district · school · provider`; школа видит только себя, район — свои школы, поставщик — свои линии. Запрет по умолчанию: роль без заданной области не видит ничего; кэши разделены по области видимости |
| Rate limiting | 120 запросов/мин на агента, 600 на пользователя (Redis-счётчики) |
| Неизменяемый аудит | append-only журнал со сцепленными SHA-256 хэшами; `/api/auth/audit` проверяет целостность цепочки |
| Минимизация данных | собираются только сетевые метрики и служебные контакты; персональные данные учащихся не хранятся |

## 3. Ключевые возможности

### Smart Sync — защита от Thundering Herd
Когда сотни офлайн-агентов одновременно возвращаются в сеть, `POST /api/agent/measurements/batch`
**не пишет замеры в БД**: пакет целиком сохраняется в `sync_batches.payload` и ставится в
очередь, клиент получает `202 Accepted`. Запись выполняют фоновые воркеры с ограниченным
параллелизмом и bulk-insert.

**Что гарантируется.** `202` означает «пакет надёжно принят»: он лежит в БД до успешной записи,
переживает перезапуск сервиса (`recover_pending`) и повторяется при сбое (до 5 попыток, затем
остаётся в `failed` для разбора). Запись идемпотентна (замер с тем же `device_id`+`timestamp`
пропускается). Агент удаляет локальную копию **только после** `GET /measurements/batch/{id}` →
`done`, а не на `202`. При переполнении очереди сервер отвечает `503` с `Retry-After` и пакет
остаётся у агента. **Чего нет:** очередь в памяти процесса рассчитана на один процесс API
(для нескольких — `CELERY_BROKER_URL`); гарантия относится к принятым пакетам — замер,
не покинувший ПК (диск агента утерян), восстановить нельзя. При заданном `CELERY_BROKER_URL`
в брокер уходит только номер пакета с `rate_limit`, размазывающим пик. Агент стартует
выгрузку со случайной задержкой.

### Свежесть данных и режим демонстрации истории
Статус школы верен только пока замер свежий (по умолчанию не старше 90 мин, настраивается).
Иначе школа получает статус **«Нет свежих данных»** — отдельный от «Нет соединения» (замер был,
связи нет): на карте, в списках, в диагностике и прогнозе, с временем последнего замера
и возрастом данных. Средние по области и «доля нормы» без свежих замеров не показываются,
пустая доска вердиктов сопровождается пометкой, что это отсутствие данных, а не отсутствие
отклонений. Кнопка **«Демо истории»** переводит все экраны на момент последнего замера в базе
(параметр `as_of`), с заметным баннером «это не текущие данные». Состояние, записанное позже
`as_of`, в этом режиме не показывается.

### Основная линия и рабочие места
Состояние школы определяет **основная линия**, измеренная точкой мониторинга (`Line`,
`Device.line_id`; агент: `VKO_DEVICE_TYPE=Шлюз`, `VKO_LINE_CODE`, `VKO_LINE_ROLE`). Резервная
линия ведётся отдельно и школу не «красит». Обычные рабочие места (ноутбук на плохом Wi-Fi)
оцениваются отдельно — сводка `workstations` в карточке школы — и на статус школы, аналитику
SLA, претензии и прогноз не влияют. Более старый догруженный замер не затирает более свежий.
Школа без точки мониторинга основной линии статуса не получает.

### Пороги, статус и инциденты (ТЗ п.11, п.18)
Замер оценивается по пяти показателям: Download ≥ 20 Мбит/с (и не ниже 60% договорной
скорости — что строже), Upload ≥ 20 Мбит/с, Ping ≤ 100 мс, Jitter ≤ 30 мс, потери ≤ 2%;
доступность ≥ 99% считается за период. Пороги хранятся в БД версиями, меняются администратором
(`PUT /api/admin/thresholds`, вкладка «Управление»); каждый замер хранит применённую версию
и результат оценки. Инцидент создаётся не по одному плохому замеру, а после **N подряд**
замеров «Критично»/«Нет соединения» (по умолчанию 3, настраивается).

### Выгрузка (ТЗ п.9)
`GET /api/web/export` — CSV и XLSX: школа, ПК, период, статус, набор столбцов; либо сводка по
школам (замеров, средний/минимальный Download, средний Upload и Ping, проблемных замеров и их
доля, случаи отсутствия интернета). Область видимости роли применяется; время в файле — UTC.

### Рейтинг организаций и хранение данных

`GET /api/web/rating?days=7|30|90` — рейтинг школ в области видимости пользователя (RBAC); вкладка «Рейтинг».
Оценка 0–100 = 50% соответствие SLA + 25% доступность + 25% скорость к договору, по замерам точек
мониторинга основных линий. Уровни: ≥90 «Отлично», ≥75 «Хорошо», ≥60 «Удовлетворительно», ниже — «Проблемная».
Школы с менее чем 10 замерами за период не ранжируются (не «худшие», а «мало данных»). К каждой строке
прилагается изменение оценки и места относительно предыдущего периода такой же длины.
`GET /api/web/rating/history?days=90[&school_id=N]` — дневная динамика (оценка, SLA, доступность, скорость, ping).

Замеры хранятся не меньше 92 дней (квартал): `RETENTION_DAYS` (по умолчанию 120) не может быть меньше этого пола;
суточная очистка считает срок от самого свежего замера в базе, поэтому остановка сбора историю не стирает.
Рейтинг считается на лету из сырых замеров (кэш 60 с); при росте базы — суточная сводка.

### Аналитика SLA и доказательная база претензии
`services/predictive.py` — статистический анализ накопленных замеров (без обучаемых
моделей): агрегация по дням недели и часам суток, сравнение с базовой линией и порогами
SLA. Находит воспроизводимые паттерны деградации («каждый понедельник просадка на 38%»),
считает соответствие SLA, стабильность канала и оценку риска 0–100 с прогнозом.
На этой базе `GET /api/ai/sla-report/{school_id}` формирует **PDF-акт фиксации нарушения SLA** —
приложение к досудебной претензии, а `POST /api/ai/claim/{incident_id}` генерирует саму
претензию (Gemini, с детерминированным юридическим шаблоном как fallback).

### «Виновник» — ML-атрибуция: гипотеза об источнике деградации

Главный контраргумент провайдера на любую претензию — «проблема у вас внутри». Граница
просадки сужает круг причин, но **конкретную причину не доказывает**, поэтому система выдаёт
*предполагаемый источник* и оценку достаточности данных:

| Что показывают замеры | Предполагаемый источник | Кто проверяет |
|---|---|---|
| 1 ПК из N, соседние ПК в норме | отдельный ПК или его подключение | сисадмин школы |
| все ПК школы, соседние школы в норме | уровень школы: ЛВС, роутер **или индивидуальная линия провайдера** | школа и провайдер |
| все сопоставимые школы провайдера в районе | узел провайдера | провайдер |
| все провайдеры района | магистраль / энергоснабжение | магистральный оператор |

Сравнение с соседями ничего не стоит без соседей. Поэтому: соседи без свежих замеров не считаются
«здоровыми», а исключаются из сравнения; при нулевом числе сопоставимых школ провайдера в районе
вердикт «источник не определён» (гипотеза модели видна, но в претензию не идёт); при малом
числе соседей оценка ограничена; оценка модели не превышает 0.9 / 0.6 / 0.3 при достаточных /
ограниченных / недостаточных данных. «Основание для претензии» выставляется только при
достаточных данных и стороне провайдера. Нет замеров — состояние «нет свежих данных», а не «норма».

**Слой 1 — сезонный базис.** Порог SLA (60% договора) не видит деградацию внутри
нормы: канал 100 Мбит/с, просевший с 95 до 62, формально «Норма». Поэтому качество
сравнивается не с договором, а с собственной нормой ПК в этот час и тип дня —
робастно, по медиане и MAD (48 корзин на агент).

**Слой 2 — классификатор радиуса поражения.** 13 признаков: доля поражённых ПК школы,
состояние шлюза, согласованность просадки, доли поражённых школ того же провайдера
в районе / других провайдеров в районе / того же провайдера в других районах, тип
линка и уровень Wi-Fi-сигнала. Вердикт сопровождается вкладом каждого признака —
объяснимо для оператора и для суда.

**Слой 3 — прогноз.** Вероятность выхода за SLA в ближайшие 6 часов по состоянию
канала за 1/6/24 ч и контексту района. Метки берутся прямо из истории замеров.

Результат подставляется в `POST /api/ai/claim/{id}` и в PDF-акт отдельным разделом
«Предполагаемый источник нарушения» — с ограничениями данных, без утверждения о вине. Если
источник на уровне школы, система предупреждает: перед претензией исключите оборудование
школы (индивидуальную линию провайдера это не исключает).

**Как это обучено.** Модель — мультиномиальная логистическая регрессия на чистом
Python (`services/ml/linmodel.py`): десяток признаков, обучение за секунды, веса
лежат читаемым JSON. Внешних ML-зависимостей нет намеренно — система ставится на
школьные серверы и должна работать офлайн, где колёса под текущий Python могут быть
недоступны.

Разметка берётся из таблицы `fault_events`. Для холодного старта её наполняет
симулятор отказов в `bootstrap.py`: аварии рождаются на четырёх уровнях иерархии и
спускаются на замеры, порождая ту самую синхронность. В эксплуатации туда же ложатся
подтверждённые вердикты операторов (`POST /api/ml/verdict/{id}`) — цикл замыкается,
и переобучение опирается уже на реальные инциденты.

**Честно о метриках.** На отложенной выборке демо-данных (пороги ТЗ) атрибуция даёт
accuracy 0.981 и macro-F1 0.981, прогноз — 0.87 и 0.856. Высокие числа атрибуции
объясняются тем, что симулятор рисует чистые границы поражения; это корректная
оценка обучаемости на синтетике, но **не** продуктовая метрика. Настоящая проверка —
доля совпадений с вердиктами операторов после месяца эксплуатации, и она видна в
`/api/ml/model-info` по мере накопления меток. Прогнозные вероятности подрезаны
диапазоном 1–99%: взвешивание классов при обучении смещает калибровку, и модель не
вправе заявлять полную определённость.

### Динамическая конфигурация агента
Сервер сам управляет расписанием тестирования: «Норма» — 15 мин, «Нестабильно» — 3 мин,
«Критично» — 1 мин с переходом в углублённую диагностику. Новая конфигурация возвращается
в ответе на каждый замер (`config_version`), оператор может переключить режим вручную из
карточки ПК.

## 4. Запуск системы

```bash
# 1. Backend
cd backend
pip install -r requirements.txt
python bootstrap.py              # миграция схемы + демо-данные (идемпотентно)
python main.py                   # http://localhost:8000/docs

# 2. Frontend
cd frontend
npm install
npm run dev                      # http://localhost:5173

# 3. Консольный ПК-агент
cd agent
pip install -r requirements.txt
export VKO_SCHOOL_CODE=VKO-UK-001
export VKO_ENROLL_SECRET=<код из раздела «Управление»>
export VKO_DEVICE_TYPE=Шлюз          # точка мониторинга основной линии; без него — рабочее место
export VKO_LINE_CODE=VKO-UK-001-L1   # какую линию измеряет (резервная: другой код + VKO_LINE_ROLE=backup)
python agent.py

# 4. Проверки (временная БД, боевую не трогают)
cd backend && python -m unittest discover -s tests
```

При старте backend сам добавляет недостающие колонки (`migrate_schema`), создаёт основные линии
и первую версию порогов; `bootstrap.py` для этого не обязателен.

Продакшн-конфигурация задаётся переменными окружения:

```bash
DATABASE_URL=postgresql+psycopg://user:pass@db:5432/vko
REDIS_URL=redis://cache:6379/0
CELERY_BROKER_URL=amqp://guest:guest@rabbitmq:5672//
JWT_SECRET=<секрет>
REQUIRE_MTLS=true
GENAI_TOKEN=<ключ Gemini>
DEBUG=false
```

## 5. Трей-агент (Windows и Linux)

Для клиентских рабочих мест реализовано фоновое приложение системного трея с графическим интерфейсом. Оно вынесено в отдельную ветку `feature/tray-agent`:

```bash
git checkout feature/tray-agent
```

В ветке содержатся:
- Нативная иконка состояния сети в системном трее Windows и Linux.
- Окно оперативного статуса канала и диалог первичной настройки.
- Локальный буфер замеров на SQLite для гарантированной доставки при обрыве связи.
- Готовые скрипты сборки в один исполняемый файл без внешних зависимостей (`.exe` для Windows, бинарник для Linux) и поддержка добавления в автозагрузку системы.

Подробная инструкция по установке и сборке приведена в `README.md` соответствующей ветки.

## 6. Интерфейс

Светлая панель на **Manrope** (интерфейс) и **JetBrains Mono** (числовые метрики).
Знак приложения и подвал бокового меню используют логотипы проекта: Акимат ВКО,
Oskemen Hub и «Цифровой ВКО» (`frontend/public/logos/`).

- **Демо истории** — переключатель в шапке: экраны показывают состояние на момент последнего
  замера в базе; пока замеров нет, шапка и баннер прямо говорят «нет свежих данных».
- **Карта области** — тепловая карта качества связи, точки школ и спутниковая подложка;
  всплывающая карточка на маркере, KPI-полоса, правая колонка со сводкой, рейтингом риска
  нарушения SLA, инцидентами и проблемными ПК. Границы карты зафиксированы в пределах
  Восточно-Казахстанской области.
- **Карточка школы** — метрики канала, графики скорости/задержки, анализ соответствия SLA
  с паттернами деградации, список ПК-агентов, контакты, инциденты, выгрузка акта PDF.
- **Диагностика** — доска вердиктов «кто виноват» с доказательной базой по каждой
  организации, распределение ответственности по области (провайдер против школы),
  очередь прогноза пробоя SLA и карточка моделей с метриками и переобучением.
- **ПК-уровень** — по каждому компьютеру: собственная история канала, доступность агента,
  соответствие SLA, инвентарь и отпечаток оборудования, динамическая конфигурация,
  журнал офлайн-догрузок Smart Sync.

Палитра графиков (`#2F6BF6 · #0E9C8A · #D9730D · #B23A8E`) проверена на различимость
при нарушениях цветовосприятия; двойных осей нет — скорость и задержка разведены
по отдельным полотнам.

## 7. Источники данных

- **Координаты и геопозиционирование:** OpenStreetMap (Overpass API) — 181 подтверждённая организация образования ВКО (г. Усть-Каменогорск, Семей, Риддер, Курчатов и 11 районов области). Все объекты вне границ ВКО отфильтрованы.
- **Метрики качества:** синтезированы стохастическим симулятором сетевых сбоев для демонстрации работы моделей и интерфейса. В боевом режиме заменяются замерами клиентских агентов.
- **Официальный реестр:** структура данных и коды организаций согласованы со структурой портала открытых данных data.egov.kz.
