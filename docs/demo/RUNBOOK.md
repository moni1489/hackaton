# Runbook: запуск демонстрации

Рассчитан на человека, который **не видел код**. Все команды — из корня репозитория.
Операционные системы: Linux, macOS, Windows (PowerShell/CMD). Нужны Python 3.11+ и Node.js 20+.

## 0. Что получится

```
python demo.py up
```
поднимает сервер, создаёт демо-сессию и печатает в терминале **ссылку и QR-код для зрителей**.
Панель оператора — `http://<адрес>:8000/demo` (то же приложение, вкладка «Демонстрация»),
зрители — `http://<адрес>:8000/live/<id>#t=…`: ML-дашборд в реальном времени.

## 1. Один раз: установка (нужен интернет)

```
python demo.py install     # pip install -r backend/requirements.txt; npm install в frontend
python demo.py prepare     # секреты, демо-БД, запись сценария, сборка фронтенда
```

`prepare` сам:
- создаёт `backend/.env` (в git не попадает) с новым `JWT_SECRET` и паролем ведущего, **никогда не перезаписывая**
  уже существующие строки — только дописывает недостающие;
- создаёт **отдельную** демо-БД `backend/demo.sqlite` (только учётная запись ведущего; данных школ и учётных
  записей проекта в ней нет — основная БД не затрагивается);
- считает сценарий на синтетических данных и проверяет, что модели дают ожидаемый вердикт;
- пишет запись сценария для резервного режима (`frontend/public/demo-replay.json`, `demo-report.pdf`);
- собирает фронтенд так, что страницы и API открываются **с одного адреса**.

В конце печатается вход ведущего: `demo.operator@example.local / <пароль>`. Пароль лежит в `backend/.env`
(`DEMO_OPERATOR_PASSWORD`), там же его можно поменять и повторить `prepare`.

После этого шага **интернет больше не нужен** ни для подготовки, ни для показа.

## 2. День показа: запуск

1. Подключите ноутбук ведущего и телефоны зрителей **к одной сети** (Wi-Fi зала или точка доступа ноутбука/телефона;
   интернет в этой сети не обязателен).
2. Запуск:
   ```
   python demo.py up
   ```
   В терминале появятся: адрес панели ведущего, ссылка зрителей и QR. Порт занят? `python demo.py up --port 8010`.
3. Проверка готовности (в другом окне терминала): `python demo.py check` — все пункты `[OK]`, в конце «ГОТОВО К ПОКАЗУ».
4. Откройте панель `http://<адрес из терминала>/demo`, войдите (email и пароль из шага `prepare`).
   Это обычное приложение оператора; демонстрация — вкладка «Демонстрация» (кнопка «▶ Демо для зала» в шапке).
5. Нажмите «▶ Запустить демо». Дальше показ идёт **в обычных экранах приложения**: внизу появляется
   полоса управления (шаг, «Следующий шаг →», решение оператора, акт, сброс), а сценарий сам открывает
   нужный экран — карта → карточка школы-героя → диагностика «кто виноват» → инциденты → акт.
   Во вкладке «Демонстрация» — предпросмотр ML-дашборда, который увидят телефоны зрителей, управление,
   ниже — **ссылка и QR-код**. Если в QR оказался неверный адрес (несколько сетевых интерфейсов, VPN) —
   впишите правильный в поле «Адрес для зрителей» и нажмите «Обновить ссылку и QR».
6. Выведите QR на проектор. Зрители сканируют — на панели растёт «Зрителей».

## 3. Ход демонстрации (кнопки панели)

| Кнопка | Что делает для зрителей |
|---|---|
| ▶ Запуск | этап `normal`: школы работают штатно, данные свежие |
| Следующий этап → | по порядку: `incident_started` → `diagnostics` → `ml_result` → `operator_review` |
| (диагностика) | четыре шага появляются сами, каждые 4 с (настраивается) |
| Подтвердить вердикт / Изменить… | решение оператора → `operator_confirmed` |
| Сформировать акт | `report_ready`: обращение и PDF-акт, у зрителей появляется кнопка скачивания |
| ⏸ Пауза / ⏵ Продолжить | останавливает шаги диагностики и автоматические переходы |
| ↺ Сброс | этап `reset`: всё очищено; «▶ Запуск» начинает сценарий заново (счётчик «Запуск №» растёт) |
| «Перейти к этапу вручную» | прыжок на любой этап; назад — сбрасывает всё, что относилось к более поздним этапам |

**Этап «Решение оператора» нельзя пропустить**: «Следующий этап» неактивен, переход вперёд без решения
отклоняется сервером (в том числе таймером). Решение — «Подтвердить вердикт» или «Изменить…» (выбрать другой
источник). Заметка в поле — только для журнала, зрителям она не показывается.

### Автоматический режим

Блок «Автоматический режим» → режим «Автоматический», интервалы (секунды на этап; **0 — ждать ведущего**) →
«Применить». Дальше после «▶ Запуск» этапы идут сами; на «Решение оператора» и в конце
(«Обращение и акт»: 0 по умолчанию) сценарий останавливается. Обратный отсчёт виден зрителям и в панели.
Тот же режим можно задать при создании сессии.

## 4. Повторный запуск

«↺ Сброс» → «▶ Запуск». Всё воспроизводится один в один (это проверено тестами): те же цифры, тот же вердикт.
Сессию не нужно пересоздавать, зрителям не нужно заходить заново. Если нужна новая ссылка — «Закрыть сессию» и
«▶ Запустить демо» (старые ссылки перестанут работать).

## 5. Остановка

Ctrl+C в окне терминала с `demo.py up`. Панель: «Закрыть сессию» — ссылки зрителей перестают работать,
у зрителей появляется «Демонстрация завершена».

## 6. Дополнительные режимы

| Что | Команда |
|---|---|
| Публичный показ (наружу только демо-API и вход оператора) | `python demo.py up --public` — см. `SECURITY.md` |
| Несколько процессов + общий Redis | `docker run -d --name demo-redis -p 6379:6379 redis:7-alpine` и `python demo.py up --workers 2 --redis redis://127.0.0.1:6379/0` |
| Только сервер, без авто-сессии | `python demo.py up --no-session` |
| Новая сессия на уже запущенном сервере | `python demo.py session [--url http://хост:порт]` |
| Сброс сценария из терминала | `python demo.py reset` |
| Запись сценария без сервера | `python -m http.server 8080 --directory frontend/dist` → `http://localhost:8080/#replay` |
| Нагрузка: 50 зрителей | `python demo.py load -n 50` (сервер уже запущен) |
| Все тесты | `python demo.py test` (`--quick` — только демо) |
| Свой адрес в QR (туннель, домен) | `python demo.py up --public-url https://demo.example.org` |
| Основная БД проекта вместо `demo.sqlite` | `python demo.py prepare --main-db` и `up --main-db` (не для публичного показа) |

Redis необязателен. Без него сервер работает в памяти процесса (один процесс) и пишет в лог
«Redis недоступен … работаем в памяти процесса». Если Redis уже запущен на `localhost:6379`, он подхватится сам.

## 7. Настройки (`backend/.env`, образец — `backend/.env.example`)

`DEMO_MODE` (включается командой `up`), `DEMO_PUBLIC`, `DEMO_PUBLIC_URL`, `DEMO_OPERATOR_EMAIL`,
`DEMO_OPERATOR_PASSWORD`, `DEMO_VIEWER_TTL_MIN` (срок ссылки, по умолчанию 240), `DEMO_SESSION_TTL_MIN`,
`DEMO_MAX_SESSIONS`, `DEMO_MAX_VIEWERS`, `DEMO_RATE_LIMIT_*`, `REDIS_URL`.

## 8. Разработка (по желанию)

```
cd backend && DEMO_MODE=true DATABASE_URL=sqlite:///demo.sqlite uvicorn app.main:app --reload --port 8000
cd frontend && VITE_API_URL= npm run dev     # прокси /api → :8000 настроен в vite.config.js
```

## 9. Если что-то не работает

Сначала `python demo.py check`. Затем `FAILOVER_PLAN.md`. Частые случаи:

| Симптом | Причина / решение |
|---|---|
| «Порт 8000 занят» | другое приложение; `python demo.py up --port 8010` |
| **GitHub Codespaces:** ссылка с `10.x.x.x` не открывается | внутренний IP снаружи недоступен. `demo.py` сам подставляет адрес `https://<имя>-<порт>.app.github.dev`; у порта во вкладке PORTS выберите **Port Visibility → Public** (`gh codespace ports visibility 8010:public -c $CODESPACE_NAME`), иначе телефоны без входа в GitHub не откроют. Публичный порт — используйте `up --public` |
| Телефон не открывает ссылку | разные сети / VPN / фаервол; проверьте адрес в QR, откройте порт в фаерволе, `--public-url` |
| В QR «localhost» | панель открыта как `localhost`; в панели впишите адрес компьютера в сети |
| «frontend/dist не собран» | `python demo.py prepare` |
| Вход ведущего не проходит | пароль в `backend/.env` → `python demo.py prepare` (приводит учётную запись к нему) |
| «Слишком много попыток входа» | подождите минуту (лимит `DEMO_LOGIN_RATE_LIMIT`) |
| Публичный режим не стартует | сработала защита: секрет/пароли по умолчанию; используйте `up --public` без `--main-db` |
